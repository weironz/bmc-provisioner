# ASRR 8U16X GNR2 B300 首次登录与默认密码兼容说明

本文记录 `ASRR 8U16X-GNR2 B300` 在 BMC 初始配置时出现的首次登录限制，以及
`bmc-provisioner` 对该限制的处理方式。它适用于 BMC 仍使用 DHCP 获取地址、需要由
本工具改为静态 IPv4 的现场流程。

## 现象

本次验证设备处于出厂初始状态时，BMC 的默认凭据为：

| 字段 | 值 |
| --- | --- |
| 用户名 | `admin` |
| 当前默认密码 | `admin` |

首次用浏览器访问 BMC 时，ASRR/AMI 页面会要求“必须修改预设置使用者密码”。在完成这
一步之前，设备不会允许以该账号执行正常的管理操作。

默认密码只应作为首次接入的临时凭据。实际交付前应以设备标签、厂商随附资料或资产记录
为准；若现场已初始化过 BMC，不能再假定它仍是 `admin/admin`。

## 为什么原来的 Redfish 流程会失败

标准流程是：使用当前账号密码读取 Redfish Service Root、`AccountService`、账号资源和
`EthernetInterface`，再通过 Redfish 修改密码与静态网络。

这台设备在强制改密状态下存在一个兼容性限制：

1. 它允许创建 Redfish 会话，并返回 `Base.1.12.PasswordChangeRequired`；这说明
   `admin/admin` 本身是有效凭据。
2. 但它同时拒绝访问完成标准改密所需的 `AccountService`/账号资源。
3. 因此仅使用 HTTP Basic 认证做 Redfish 资源发现时，会表现为“认证失败”，即使默认
   密码正确。

Redfish 规范期望处于 `PasswordChangeRequired` 状态的客户端仍可访问当前账号并执行受限
改密操作。该机型的固件没有完整提供这一条标准路径，问题不在 DHCP、lessor 或目标静态
IP 参数。

## bmc provisioner 的解决方案

包含该兼容逻辑的当前本地构建，在**全部**满足以下条件时才启用 AMI 兼容分支：

1. 先用标准 Redfish Basic 认证发现资源；
2. 发现因认证受限无法继续；
3. 读取 BMC 的公开前端脚本，确认同时存在 AMI 的 `/api/session` 与
   `/api/updatenew_password` 首次登录接口；
4. 操作者在凭据档案中提供当前默认密码和新的密码。

满足条件后，工具会：

1. 通过受限的 AMI HTTPS 会话完成一次首次密码修改；
2. 立即关闭该会话；
3. 使用新密码回到标准 Redfish 流程；
4. 动态发现实际可配置的 BMC 管理网卡；
5. 通过 Redfish 禁用 DHCP 并写入目标静态 IPv4、前缀和网关；
6. 在新地址重新验证 Redfish 登录。

也就是说，厂商 Web API 只承担无法通过标准 Redfish 完成的“首次改密”过渡；网卡选择、
静态地址配置和最终验证仍由 Redfish 完成。

## 使用步骤

1. 让 lessor 为 DHCP 模式的 BMC 分配地址，并确认清单中的 IP/MAC。
2. 在 bmc-provisioner 的凭据档案中填写 `admin`、当前默认密码 `admin` 和符合现场密码
   策略的新密码。
3. 为该 BMC 行填写目标静态 IPv4；前缀与网关使用已保存的网络默认值或按现场调整。
4. 勾选该行并执行 IP 变更配置。
5. 等待任务显示已在目标地址完成 Redfish 登录验证，再使用新密码访问 BMC。

若首次密码修改失败，工具不会继续尝试写入静态网络。请先确认新密码符合 BMC 的长度、
复杂度与历史密码策略，并确认当前账号确实仍是出厂/首次登录状态。

## 安全与边界

- 兼容分支仅在明确识别到上述 AMI 前端接口时执行，不会对其他厂商或普通 Redfish BMC
  猜测 Web API。
- 连接仍使用 HTTPS；自签名证书需要先读取并确认 SHA-256 指纹，不会静默跳过 TLS 校验。
- 密码不会写入本地 SQLite 清单或任务历史。桌面端使用系统凭据管理器；容器模式的密码只
  保存在运行中服务的内存中。
- 若 BMC 已完成首次改密，工具不会使用 AMI 兼容接口，而是直接走标准 Redfish 流程。
